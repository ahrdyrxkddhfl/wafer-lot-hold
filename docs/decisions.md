# 결정 기록

기술 선택과 버린 대안을 한두 줄씩 적는다.

## 0단계

- **모델 코드는 복사하지 않고 import한다.** 복사본이 원본과 어긋나면 가중치는 불러와지는데 판정만 틀어질 수 있다.
  노트북에만 있는 코드(pickle 호환 처리, 축소, 분할)는 import할 수 없어 출처 셀을 주석으로 적어 옮겼다.
- **분할은 원본 절차로 다시 만들고 기존 `split.npz`와 한 원소씩 비교한다.** 기존 파일에는 lotName이 없어서
  Lot 정보를 붙이려면 다시 만들어야 하고, 같은 분할임을 증명해야 12번 모델의 점수를 그대로 쓸 수 있다.
- **0단계에는 pytest를 두지 않는다.** 웨이퍼 저장소 가상환경에 pytest가 없고, 그 저장소는 수정하지 않는다.
  대신 검증 단계(해시, 분할 비교, 점수 재현)가 실패하면 exit 1로 멈추고 산출물을 쓰지 않는다.
- **산출물은 CPU 판정으로 만든다.** 다른 컴퓨터에서도 같은 결과가 나오게 하기 위해서다. 원래 점수는 MPS에서
  나왔으므로 MPS로도 판정해 비교한다(두 장치 예측 차이 0장).
- **웨이퍼 ID는 `{lotName}_W{waferIndex:02d}`.** Test 안에서 중복이 없음을 확인했다. 원본 추적용으로
  `src_row`(LSWMD.pkl 원본 행 위치)도 함께 남긴다.
- **정답 라벨은 판정 파일과 다른 파일·폴더(`evaluation/`)에 둔다.** 정답이 섞이면 AI 판정이 아니라 정답으로
  Lot을 멈추는 실수가 생길 수 있다.
- **정답 파일에 `label_source`(labeled/unlabeled)를 남긴다.** 원본 전처리가 라벨 없는 웨이퍼를 `none`으로 넣었기
  때문에, 평가 때 라벨 없음을 정상으로 치지 않고 따로 세기 위해서다.
- **웨이퍼 저장소 경로는 상대경로 기본값 + 환경변수 `WAFER_REPO`.** 절대경로는 계정 이름이 공개되고 다른 컴퓨터에서 맞지 않는다.
- **설정은 YAML(`pyyaml`).** 값마다 주석을 달 수 있고 웨이퍼 저장소 환경에 이미 있다. JSON은 주석을 달 수 없어 버렸다.

## 1단계

- **ORM과 마이그레이션 도구를 쓰지 않는다.** 잠금(`FOR UPDATE`)과 트랜잭션 범위가 SQL에 그대로 보이게 하기 위해서다.
  테이블 정의는 `schema.sql` 하나로 관리한다(버전이 하나뿐인 프로젝트).
- **연결은 autocommit으로 열고 함수 안에서 `with conn.transaction():`으로 트랜잭션을 연다.** 어디서 어디까지가
  한 트랜잭션인지 코드에서 바로 보인다. 바깥 트랜잭션 안에서 부르면 savepoint가 된다(psycopg 3 동작).
- **잠금이 정상 경로, 제약이 마지막 방어선.** 같은 Lot·같은 설비에 대한 요청은 행 잠금으로 줄 세워 깔끔한 규칙 오류로
  거절하고, 부분 유일 인덱스 등 제약은 잠금이 빠졌을 때를 대비한다. 제약 위반은 규칙 오류로 바꾸지 않고 그대로 실패시킨다
  (바꾸면 잠금이 빠져도 테스트가 통과해 잠금이 빠진 것을 알아챌 수 없다).
- **설비 잠금은 `FOR SHARE`가 아니라 `FOR UPDATE`.** `FOR SHARE`는 여러 트랜잭션이 동시에 잡을 수 있어 두 Lot이 같은 설비를
  함께 "비어 있음"으로 읽는다. 실제로 `FOR SHARE`로 바꾸면 I11 동시성 테스트가 실패했다.
  (1단계 보완에서 Lot·설비 모두 `FOR NO KEY UPDATE`로 바꿨다. 아래 "1단계 보완" 참고.)
- **잠그는 순서는 항상 Lot → 설비.** 순서가 섞이면 두 트랜잭션이 서로를 기다리는 교착이 생길 수 있다.
  (1단계 보완에서 설비 고장 처리만 설비 → Lot 순서가 됐다. 아래 참고.)
- **Hold 여부를 Lot 상태 값에 넣지 않는다.** 열린 Hold 행과 상태 값을 둘 다 두면 둘이 어긋날 수 있다.
- **재검사(RETEST)는 작업 지시를 새로 만들지 않고 `inspect_round`만 올린다.** 한 Lot은 한 공정을 한 번만 처리한다는
  제약(I2)을 유지하면서 같은 웨이퍼의 재판정을 다른 차수로 받기 위해서다.
- **폐기(I10)는 트리거 없이 서비스 검사로 막는다.** 이전 값과 비교하려면 트리거가 필요한데, 모든 변경이 Lot 잠금을 거치는
  서비스 함수로만 일어나므로 얻는 것에 비해 설명 부담이 크다.
- **테스트는 테스트 전용 DB에서 매 테스트 전에 TRUNCATE로 정리한다.** 동시성 테스트는 연결 두 개가 각자 커밋하므로
  롤백으로는 격리되지 않는다. 모든 테스트가 같은 방식을 쓰고, 끝이 아니라 시작 전에 비워 실패한 테스트의 데이터를 볼 수 있게 한다.
- **동시성 테스트는 행을 읽은 직후 0.3초 기다리게 해(monkeypatch) 경쟁 구간을 넓힌다.** 잠금이 없을 때 실패가
  우연이 아니라 매번 재현되게 하기 위해서다.
- **PostgreSQL 17.11로 고정(compose와 CI 같은 버전).** 18은 컨테이너 데이터 경로가 바뀌어 볼륨 설정이 달라진다.
- **python-dotenv로 `.env`를 읽는다.** 테스트와 스크립트가 셸에서 따로 export하지 않아도 같은 비밀번호를 쓴다.

## 1단계 보완

- **설비 고장(DOWN)은 받고 계획 정비(MAINTENANCE)는 거절한다(I12).** 정비는 미룰 수 있으니 처리 중인 Lot이 끝난 뒤에 하게 하고,
  고장은 이미 일어난 일이라 거절할 수 없으므로 받되 그 설비에서 처리 중인 Lot을 같은 트랜잭션으로 Hold(`EQUIPMENT_DOWN`)한다.
  Hold에는 그 설비 상태 변경 이력(`trigger_equipment_history_id`)을 남겨, Hold 기록만으로 무엇 때문에 멈췄는지 알 수 있게 한다.
- **재검사(RETEST)는 Lot이 INSPECT에서 처리 중일 때만 받는다.** 처음에는 공정과 상관없이 받아 `inspect_round`만 올렸는데,
  STEP_1 대기 Lot에서 재검사하면 차수가 2가 되어 나중에 INSPECT에서 받을 1차 판정이 차수 불일치로 거절되는 버그였다
  (검토에서 재현, 테스트 `test_retest_only_allowed_at_inspect`).
- **이미 처분된 Hold의 재처분은 작업 지시(I3)와 같은 방식.** 같은 내용이면 기존 처분을 돌려주고, 다르면 `HOLD_CLOSED`.
- **설비 고장 처리의 잠금 순서와 교착.**
  - 고장 처리는 설비를 먼저 잠그고, 그 설비에서 처리 중인 Lot을 찾아 잠근다(설비 → Lot). 다른 함수와 순서가 반대다.
  - 처음 분석: "Lot을 잡은 채 설비를 기다리는 함수는 track_in뿐이고, track_in은 처리 중인 Lot(I7)을 설비 잠금 전에 거절하므로
    교착이 없다"고 판단했다.
  - 검토에서 빠진 경로를 찾았다: track_in이 다른 공정 설비 여부(EQUIPMENT_STEP)를 설비를 잠근 뒤에 확인해서, 다른 공정 설비로
    잘못 온 요청이 Lot을 잡은 채 그 설비를 기다릴 수 있었다. 설비의 공정은 바뀌지 않는 기준정보이므로 잠금 없이 먼저 읽어 확인하게
    고쳤다. 전제: "공정-설비 확인은 잠금 전, 처리 중 확인은 설비 잠금 전". 이 전제는 lock_timeout을 건 결정적 테스트로 지킨다
    (`test_equipment_step_is_checked_without_waiting_for_equipment_lock`, 고치기 전에는 LockNotAvailable로 실패).
  - 그래도 동시성 테스트(설비 DOWN과 그 설비의 track_out을 동시에)에서 실제 교착(DeadlockDetected)이 났다. 원인은 코드에 보이지 않는
    잠금이었다. track_out은 Lot을 잠근 뒤 `lot_history`에 `equipment_id`를 넣는데, PostgreSQL은 외래키를 확인하려고 참조하는 설비 행에
    `FOR KEY SHARE` 잠금을 건다. 고장 처리가 설비에 건 `FOR UPDATE`는 이 잠금과 충돌하므로, track_out이 Lot을 잡은 채 설비를 기다리고
    고장 처리는 설비를 잡은 채 Lot을 기다렸다. 처음 분석도, 검토도 이 숨은 잠금을 놓쳤다.
- **행 잠금은 모두 `FOR NO KEY UPDATE`.** "기본키는 바꾸지 않고 다른 열만 바꾼다"는 잠금으로, 외래키 확인의 `FOR KEY SHARE`와 충돌하지
  않는다. 서로는 충돌하므로 같은 Lot·같은 설비를 동시에 바꾸지 못하는 직렬화는 그대로다(I7·I11 동시성 테스트 통과, 잠금을 빼면 실패).
  이 프로젝트는 기본키를 바꾸지 않으므로 Lot·설비 모두 이 방식으로 통일했다. 지금 Lot 쪽에는 문제가 없지만, 2단계에서 Lot을 참조하는
  행을 넣는 경로가 생기면 같은 종류의 숨은 대기가 생길 수 있기 때문이다.
  - 버린 대안 1: 고장 처리도 Lot → 설비 순서로 잠그기(잠금 없이 읽고 → Lot 잠금 → 설비 잠금 → 다시 읽어 다르면 오류). 다시 시도하는
    경로가 생기고 그 경로를 결정적으로 테스트하기 어렵다.
  - 버린 대안 2: track_out의 이력에서 `equipment_id`를 빼기. 숨은 잠금은 사라지지만 이력에서 어느 설비였는지 잃는다.
- **검사 공정 이름은 `mes/service.py`의 `INSPECT_STEP` 상수.** config 구조를 바꾸지 않고, 기준정보를 넣을 때 config route에 이 공정이
  없으면 멈춘다.

## 4단계

- **Lot 단위 분할은 `StratifiedGroupKFold`.** lotName을 그룹으로 묶어 같은 Lot이 두 분할에 걸치지 않게 하면서, 클래스 비율을
  전체와 비슷하게 맞춘다. 5묶음 중 하나를 Test, 나머지를 4묶음으로 나눠 하나를 Valid로 써서 원래 60/20/20과 같은 비율로 맞췄다.
  `GroupShuffleSplit`은 그룹은 지키지만 층화를 하지 않아, Near-full(149장)처럼 적은 클래스가 한 분할에 몰릴 수 있어 버렸다.
- **학습은 12번과 같은 설정·같은 30,519장, 학습 루프는 웨이퍼 저장소의 `train_model`을 import.** 두 방식의 차이가 분할 방식
  하나뿐이어야 비교가 된다. 설정값은 `02-exp.ipynb` 셀 16에서 config로 옮겼다.
- **학습은 MPS, 판정 파일은 CPU.** 원래 12번이 MPS에서 학습했으므로 같은 장치를 썼다. MPS 학습은 결정론적 연산이 보장되지 않아
  같은 seed로 다시 돌려도 결과가 조금 다를 수 있다. 판정은 다른 컴퓨터에서도 같은 결과가 나오도록 CPU로 한다.
- **MES에 올릴 판정은 시험용 Lot의 원본 전체 웨이퍼.** Lot 단위 Test의 Lot은 어떤 웨이퍼도 학습에 쓰이지 않았으므로, 축소
  데이터에 없던 웨이퍼(라벨 없음, 뽑히지 않은 none)까지 Lot 전체를 판정해야 실제 공정처럼 "Lot 하나가 통째로 검사를 받는" 데이터가 된다.
- **새 체크포인트는 `artifacts/`(커밋 안 함), 해시만 판정 파일과 README에 기록.**

## 4단계 보완: 정지 규칙 기준값은 검증용 Lot으로 고른다

- **개수·확률 기준을 다시 후보에 넣는다.** 처음에 쓰지 않기로 한 이유는 0단계 데이터의 Lot이 대부분 1~2장이었기 때문인데,
  MES에 올리는 시험용 Lot은 원본 웨이퍼 전부라 대부분 25장이다. 비율 기준은 여전히 쓰지 않는다.
- **기준값은 검증용 Lot(2,368개)의 원본 웨이퍼 전부를 Lot 단위 모델로 판정해 고른다.** 시험용 Lot으로 고르면 시험 결과에 맞춰 고른
  셈이 된다. 검증용 Lot은 가중치 학습에는 쓰이지 않았고 멈출 에폭 선택에만 쓰였다. 그래서 완전히 처음 보는 데이터는 아니지만,
  시험용 Lot을 건드리지 않고 기준을 고를 수 있는 데이터다. 정한 기준은 3단계에서 시험용 Lot에 한 번만 평가한다.
- **"멈춰야 할 Lot"은 정답 라벨에 같은 규칙(유형, 최소 장수)을 적용해 정의한다.** 라벨 없는 웨이퍼는 알 수 없으므로 정답 계산에서 빼고,
  라벨 있는 웨이퍼가 0장인 Lot은 괜히 멈춤·놓침 계산에서 뺀다. 유형이나 최소 장수를 바꾸면 "멈춰야 할 Lot"의 정의도 바뀌므로,
  기준 규칙(전체 유형·1장)의 정답으로 센 놓침을 함께 적어 같은 잣대로 비교할 수 있게 했다.
- **후보는 기준 규칙에서 한 번에 한 변수만 바꾼다.** 조합을 다 돌리면 표가 커지고 검증용 Lot에 과하게 맞춘 기준을 고르기 쉽다.
  정지 대상 유형 후보는 검증용 Lot의 라벨 있는 none 웨이퍼에서 오판정이 많은 유형부터 빼는 순서로 만들었다.
